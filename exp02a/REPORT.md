## 0. 结论摘要

【实测】EXP-02 报告中的 45–61 KB/查询确实只是 **ID + 距离下界**。在声明的基线假设
（ACL 16 B + TTL 8 B + 其他 8 B = 32 B/候选）下，模型 B 的达标成本为 **222–298 KiB/查询**，
是下界的 **5.0 倍**；模型 C 为 **312–418 KiB/查询**且需要 3 条消息，是下界的 **7.0 倍**。

【实测】E3 在默认「客户端本地过滤、无反馈」下，三组策略对的服务端可观测泄露均为 **0.000**；
原 `output_id_leakage`（0.942–0.997）只属于 `O_client`。一旦客户端把 Top-K ID 反馈给服务端，
服务端可观测泄露立即回到 0.942–0.997。

【实测】EXP-02 达标表把两种不同查询人口的成本并列：格子平均口径用全部 200 个查询，
单查询口径只用 20–50 个达标查询。24/24 个格子的预算和查询集合都不一致。这不是数据错误，
但 EXP-02 报告的表述必须收紧。

【解释】方向没被推翻，但「候选压缩」并非由数据推出的唯一解法。真正的问题被定位为：
**在服务端不可见谓词的前提下，客户端过滤所需的属性数据如何以可接受成本获得，同时保持搜索完整性可验证。**

## 2. 任务一：E3 候选过滤的数据需求

### 2.1 字段逐项确认

| 数据 | 由谁持有 | 当前是否传输 | 客户端能否独立取得 | 字节计算 |
|---|---|---|---|---|
| Candidate ID | 服务端（图节点 ID） | 是（4 B） | 否 | `id_bytes`/候选 |
| Query distance | 服务端惰性缓存 | 是（4 B） | 仅当持有完整向量 | `distance_bytes`/候选 |
| ACL 属性 | 授权数据源 / 策略方 | **否** | 仅当有本地 ACL 副本 | `acl_bytes`/候选（扫描） |
| TTL / expiration | 授权数据源 | **否** | 仅当有本地新鲜度源 | `ttl_bytes`/候选（扫描） |
| 其他谓词元数据 | 授权数据源 | **否** | 仅当有本地元数据副本 | `extra_bytes`/候选（扫描） |
| 属性引用（模型 C） | 服务端作不透明指针 | **否** | 否，需额外获取 | `reference_bytes`/候选（扫描） |

【实测】完整字段表见 `results/tables/candidate_field_requirements.csv`。

【解释】EXP-02 的 8 字节记录既无 ACL 也无 TTL，因此客户端**事实上无法执行授权过滤**；
它只能作为通信下界，不能被称为「完整协议成本」。

### 2.2 三种通信模型

| 模型 | 记录内容 | 每查询消息数 | 是否可执行过滤 | 说明 |
|---|---|---:|---|---|
| A | ID + distance | 1 | 否 | 与 EXP-02 `candidate_transfer_bytes` 完全一致 |
| B | A + ACL + TTL + 其他元数据 | 1 | 是 | 属性值随候选发送；服务端不计算匹配位 |
| C | A + 引用；属性另行获取 | 3 | 是 | 请求头 64 B + `n×ref`，响应头 64 B + `n×attr`，成本**不为零** |

【解释】模型 B 假设属性值（不是匹配位）可由服务端附带发送。若属性值本身被视为秘密，
模型 B 不成立，只能走 C 或更强的协议；本轮不设计该协议。

【猜想】属性引用或批量属性拉取可能显著降低 B 的成本，但当前没有真实属性长度与目录延迟数据，
本轮只做参数扫描，不声称已解决。

## 3. 任务二：观察者重新定义

### 3.1 可见性

| 字段 | O_server | O_client | O_network（TLS） |
|---|:---:|:---:|:---:|
| 查询 | ✓ | ✓ | — |
| 搜索轨迹 | ✓ | — | — |
| 候选 ID / 距离 | ✓ | ✓ | — |
| 授权属性值 | 仅模型 B | ✓ | — |
| 授权匹配位 | **−（所有模型）** | ✓（客户端判定） | — |
| 最终 Top-K ID | 仅 E1/E2 或 E3 有反馈 | ✓ | — |
| 消息大小 / 次数 | ✓ | ✓ | ✓ |
| 停止位置 | ✓ | — | — |

【实测】E3 无反馈、`network_tls=true` 场景：O_server 可见 8/10 字段，O_client 7/10，O_network 2/10；
E3 有反馈时 O_server 可见 10/10。完整矩阵见 `observer_visibility_matrix.png` 与对应 CSV。

### 3.2 指标重解释

【实测】`output_id_leakage` 已改名为 `cross_policy_output_distinguishability`，并新增
`server_observable_leakage`。预算 500 的三组策略对：

| 算法 | 客户端反馈 | 跨策略输出可区分性 | 服务端可观测泄露 | Top-K 观察者 |
|---|---:|---:|---:|---|
| E3 | 否 | 0.942 / 0.994 / 0.997 | **0.000 / 0.000 / 0.000** | O_client |
| E3 | 是 | 0.942 / 0.994 / 0.997 | 0.942 / 0.994 / 0.997 | O_server + O_client |
| E1 | 否/是 | 0.947 / 0.994 / 0.997 | 0.947 / 0.994 / 0.997 | O_server + O_client |
| E2 | 否/是 | 0.942 / 0.994 / 0.997 | 0.942 / 0.994 / **1.000** | O_server + O_client |

【解释】E3 旧指标并非测量错误，而是**安全解释越界**：客户端本地得到不同结果是预期的；
服务端看不到这些 ID。反过来，E2 的服务端可观测泄露达到 1.000，说明授权状态确实影响了
服务端可见的发现/停止行为——这与 EXP-02 的 E2 轨迹泄露结论一致。

【解释】「服务端可观测泄露 = 0」**不等于**协议隐私。它只说明所记录的 8 个可见信道在两组策略下无差异；
未覆盖应用层后续反馈、时序侧信道、属性服务共谋等。

## 4. 任务三：E3 完整通信成本重算

### 4.1 达标成本（格子平均口径：全部 200 查询）

属性记录 32 B/候选（声明假设）：

| 选择率 | 达标预算 | 候选数均值 | 模型 A | 模型 B | 模型 C | 消息数 A/B/C |
|---:|---:|---:|---:|---:|---:|---:|
| 1% | 200 | 7,635 | 61,080 B (59.6 KiB) | 305,400 B (298.2 KiB) | 427,688 B (417.7 KiB) | 1 / 1 / 3 |
| 5% | 100 | 5,694 | 45,552 B (44.5 KiB) | 227,760 B (222.4 KiB) | 318,992 B (311.5 KiB) | 1 / 1 / 3 |
| 10% | 100 | 5,694 | 45,552 B | 227,760 B | 318,992 B | 1 / 1 / 3 |
| 30% | 100 | 5,694 | 45,552 B | 227,760 B | 318,992 B | 1 / 1 / 3 |

Random 与 Clustered 在该口径下数值相同（因为候选数由公开图搜索决定，与授权分布无关）。

【实测】参考点：random / 10% / 预算 500，候选均值 9,466、P95 9,645：
A 均值 75,728 B / P95 77,160 B；B 378,640 / 385,800 B；C 530,224 / 540,248 B。

### 4.2 属性长度扫描

【实测】模型 B 的成本与属性记录长度线性相关：`mean = n × (8 + attr)`；
模型 C：`mean = n × (8 + 2×ref + attr) + 128`。attr 从 0 扫到 128 B 时，
预算 500 的模型 B 从约 75.7 KB 升至约 1.29 MB（random/10%）。
完整曲线见 `transfer_cost_vs_attribute_size.png` 与 `transfer_cost_by_attribute_size.csv`。

【解释】成本瓶颈是**候选数量 × 每候选属性字节**，不是单次往返的固定开销。
在当前受控图上，即使属性只有 8 B，完整成本也至少是下界的 2 倍。

## 5. 额外发现：达标成本的查询集合口径不一致

【实测】EXP-02 的 `budget_to_recall_090.csv` 中：

- `min_budget_reaching_090` 与 `distance_evaluations_at_target` 基于**格子平均召回 ≥ 0.90**，
  成本取该预算下**全部 200 个查询**的均值（包括未达标查询）；
- `min_distance_evaluations_any_query_at_target` 基于**单个查询达标**，成本只取 20–50 个达标查询。

24/24 个格子的两个预算不同、`query_populations_identical` 全为 0。例如 random / 1%：
格子口径预算 200、候选 7,635、模型 A 成本 61,080 B；单查询口径预算 50、候选 3,986、
模型 A 成本 31,888 B（仅 50 个查询）。

【解释】这两个数字回答的是不同问题，不能相减或互换。本审计的 `transfer_cost_at_recall_target.csv`
已把两种人口分开列出，未做合并。

【猜想】若论文要报告「达到 0.90 召回的代价」，更稳妥的定义是先固定查询集合再比较成本；
这需要重新运行实验，超出本轮范围。

## 6. 测试

【实测】7 项全部通过：

1. 客户端本地过滤时 Top-K ID 不暴露给服务端；
2. 客户端反馈后服务端输出观察者可见 Top-K ID；
3. 属性长度变化改变传输成本（差值严格等于 `Δbytes × n`）；
4. 模型 A 不含 ACL/TTL 字段且成本恰为 `8×n`；
5. 模型 C 的属性请求与响应成本均严格大于 0，即使属性长度为 0；
6. E3 轨迹在两种授权策略下完全一致，且底层 `traverse()` 显式拒绝非空掩码；
7. EXP-02 的 49 个基线文件哈希与 git 状态均未改变。

补充发现：`run_log()` 对 E3 会**静默剥离**传入的 `policy_mask`，硬拒绝只在 `traverse()` 层。
当前行为安全，但接口层不一致，已在测试中固定该语义。

## 7. 核心问题回答

> **在不向服务端暴露授权谓词的情况下，E3 的客户端过滤是否仍有可能保持可接受的完整通信成本？**

【实测】在当前受控图、固定入口 8817、属性记录 32 B 的声明假设下：
E3 达标（Recall@10 ≥ 0.90）的完整通信成本为 **222–418 KiB/查询、1–3 条消息**；
而 EXP-02 报告的 ID+距离下界只有 45–61 KB。服务端可观测泄露为 0（无反馈时）。

【解释】「可能」在技术上成立——轨迹不变性与召回都保住了，代价是 5–7 倍于下界的通信。
但「可接受」目前**无法判定**：属性长度没有真实测量值，候选数来自受控图而非真实 HNSW，
且服务端看到消息大小与次数（它们与候选数相关，而候选数在本实验中与策略无关）。

【解释】因此不能从本轮直接推出「候选压缩是正确解法」；本轮只把成本公式与观察者边界钉死。

【猜想】若真实系统中属性可读且每候选不超过 16 B，或候选池能被公开、策略无关的压缩规则缩小，
总成本可能回到 100 KiB 量级；两者都未经验证。

## 8. 假设与未解决问题

1. 属性长度（ACL/TTL/其他）为**扫描参数**，无真实测量值；基线 32 B 只是声明假设。
2. 模型 C 假设属性由独立服务提供；若该服务与检索服务端共谋，引用请求与获取模式会变成服务端可见信道。
3. `O_network` 默认 TLS，只看元数据；无 TLS 对照场景已给出，但未测真实中间盒行为。
4. 未建模客户端→服务端的应用层反馈、时序、缓存命中差异；这些可能重新引入泄露。
5. 未审计「服务端搜索完整性可验证」——这是原始研究问题的一半，本轮任务范围不含。
6. 达标口径另有一套查询人口；是否要重跑实验统一口径，需研究负责人决定。
7. 受控图结果不得外推为 HNSW 性能；真实索引成本保真迁移尚未进行。
