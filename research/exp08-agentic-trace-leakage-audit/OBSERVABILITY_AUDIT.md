# OBSERVABILITY_AUDIT.md — ACL 执行位置与外包检索服务可见性（R0.2.1 修订版）

任务：EXP-02-R0.1 Phase 4 初稿 → EXP-02-R0.2 Phase 1–3 修订 → EXP-02-R0.2.1 Phase 2 查询隐私对齐。性质：**威胁模型核验**，只界定"不同架构下服务端实际可见什么"，不实现 ORAM/PIR/TEE/MPC/ZKP。

**修订缘由**：R0.1 初稿在 §1.2 承认架构 A 存在"过滤→后续查询变化"的间接通道，却因该信号混合了任务自适应行为而在实验前把架构 A 降级为阴性对照，并断言"仅架构 C 自洽"。这是一处逻辑跳步——**混合信号应当通过对照实验分离，而不是在实验前判定无研究价值**。同时初稿把 TEE/ORAM/PIR/加密过滤合并为单一"架构 C"，混淆了截然不同的可见性模型。本版修正这两点，并新增服务端可观察字段契约。

---

## 0. 修订后的核心研究问题

采用一个更具体、有明确因果链的表述（取代初稿笼统的"加密过滤下的授权泄漏"）：

> **在客户端执行 ACL 过滤、Agent 根据授权上下文进行多步自适应检索的条件下，外包检索服务能否从跨调用可见的检索轨迹中，推断主体的权限范围或权限状态变化？**

这是一个**待检验的假设**，不是已成立的创新点。它比"架构 C 下授权泄漏"更贴近 Agent，因果链明确（见 §1.2）。但能否成立取决于一个必须先确定的前提：**真实、可复核的服务端观测模型**（见 §4 字段契约）。该模型可以是架构 A，也可以是某个具体的架构 C；**不得为保留候选方向而预先指定架构 C**。

## 1. 架构 A：客户端 ACL 过滤（重新核验，不再提前排除）

**流程**：检索服务返回候选文档（不感知 ACL）→ 客户端按本地 ACL 过滤 → 不同主体得到不同上下文 → Agent 基于各自上下文生成**后续检索请求** → 服务端继续响应这些后续请求。

### 1.1 必须区分的三类信号

| 类别 | 定义 | 服务端是否可见 |
|---|---|---|
| **直接泄漏** | 客户端过滤结果（哪些候选被丢弃、最终进入 Agent 的 ID） | **不可见**——过滤在客户端本地完成、未回传。这一点初稿判断正确 |
| **间接泄漏** | ACL 改变 Agent 上下文 → 后续查询内容/轮次/返回 ID/数量/时间随之变化 | **可能可见**——后续检索请求由服务端处理。这是本轮核验重点 |
| **任务语义影响** | 不同任务本身导致的多步轨迹差异（与 ACL 无关） | **可能可见**——是混杂变量，须由对照分离，而非排除理由 |

### 1.2 间接泄漏的因果链（逐环节核验）

1. **首轮**：两个权限不同的主体提交**同一任务、同一初始查询** → 服务端返回**相同候选集合**（因为服务端不感知 ACL）。故首轮轨迹在服务端视角**应当一致**——这是可检验的零点假设。
2. **客户端过滤**：两主体按各自 ACL 过滤同一候选集，得到**不同的上下文**（一个保留了某些文档，另一个丢弃）。
3. **Agent 自适应**：Agent 把各自上下文纳入 prompt，生成**后续检索查询**。上下文不同 → 后续查询**可能不同**。
4. **服务端观测**：服务端处理这些后续查询，看到其对应的返回 ID、数量、请求顺序、时间戳的变化。

**这是 Agentic RAG 相比普通单轮检索新增的泄漏通道**：单轮检索中 ACL 过滤后信号就终止了；多步检索中，过滤结果通过 Agent 的自适应决策**回灌**到服务端可见的轨迹里。

### 1.3 回答任务包四问

- **同一初始任务/查询、改变 ACL 后首轮返回是否相同？** 相同（服务端不感知 ACL，候选集由查询与索引决定）。须由对照 A 实测确认，作为零点检验。
- **后续 Agent 查询是否可能因上下文不同而变化？** 可能。这是 `AGENT_GENERATION_AUDIT.md` 已核验的机制——`search_r1.py::transform_iter` 每轮把 `search_results`（即检索到的文档文本）拼入 prompt（第 197–198 行），上下文不同必然改变下一轮生成输入。是否产生**可区分**的查询差异须实验测量。
- **服务端能否看到后续每次调用的返回 ID、数量、顺序、时间？** 有条件：取决于"每次检索是否独立请求"（字段契约第 2/3/4 项，见 §4）。若客户端批量提交则顺序不可见；若每次独立请求则可见。
- **能否归因于 ACL？** 只有在控制任务内容、初始查询、模型、语料与随机性后，把任务语义与模型随机性作为对照扣掉，剩余差异才可能归因于 ACL。**这正是 `MINIMAL_EXPERIMENT_DESIGN.md` 对照 A 的目的**，不能在此步骤之前判定"混合=无价值"。

### 1.4 裁定（修订）

架构 A **不再被降级为阴性对照**。它是本修订版研究问题的**首选主场景**：因果链最直接、最贴近 Agent、且不依赖任何本轮禁止实现的密码学机制。但它能否产生**可归因于 ACL** 的服务端信号，尚未验证，必须由对照 A/B/C 在控制任务语义与随机性后检验。混合信号是实验要分离的对象，不是排除该架构的理由。

## 2. 架构 B：服务端 ACL 过滤（维持初稿判断）

**流程**：检索服务持有 ACL 与用户身份，按用户权限过滤后返回授权文档。

- **定义性事实**：服务端持有或可查询 ACL、知道请求主体、执行过滤谓词、看到过滤前后数量与结果。
- **裁定**：若攻击者 = 检索服务本身，则 ACL 与身份是其已知输入；称它"从轨迹推断权限状态"是**把已知信息包装成推断**，循环论证，研究意义不成立。
- **唯一例外（须改攻击者定义）**：若攻击者是服务内部只接触日志、不接触 ACL 库的组件，则 ACL 对它不直接可见，轨迹可能泄漏权限。此为**扩展威胁模型**，必须单列，不能代表基础对手，也不并入基础结论。
- **结论**：架构 B 不作为主实验架构；除非显式改写攻击者定义并单独报告。

## 3. 架构 C：加密 / 隐私保护过滤（收窄为"候选类别"，不再统一视作一种模型）

初稿把 TEE、ORAM、PIR、加密策略匹配合并为"架构 C"并断言其"唯一自洽"，这是错误的——**这些机制的服务端可见性截然不同**。"服务端不持有明文 ACL"并不自动意味着"服务端能看到权限相关的结果 ID 和数量"。

### 3.1 不同机制的可见性差异（不可合并）

| 具体机制 | 服务端可见性（取决于实现） | 对本问题的含义 |
|---|---|---|
| **TEE 内过滤** | 服务端只见加密通信与 enclave I/O 模式；若填充则连 I/O 规模也隐藏 | 是否泄漏取决于 enclave 边界与填充策略；需具体系统规格 |
| **ORAM** | 隐藏访问模式（读哪个位置），但返回结果仍须传回客户端；若结果不填充则数量/ID 可能泄漏 | 访问模式被隐藏 ≠ 结果集被隐藏；需看是否对返回做填充 |
| **PIR** | 隐藏"查询了哪个索引项"，服务端看到通信量与响应批次；通常返回单个/少量项 | 查询意图被隐藏，但通信量与返回批次大小是潜在信号 |
| **加密策略匹配（如 ABE/谓词加密）** | 服务端可能看到策略结构、密文匹配是否成功、匹配结果数量 | 若匹配结果可区分，权限（能否解密/匹配）可能直接暴露 |
| **简单结果加密（无访问模式保护）** | 服务端仍见返回哪些加密句柄、数量、访问模式 | 与 SAGE 场景接近；但"无明文 ACL"不等于"无权限信号" |

### 3.2 裁定（修订）

- 架构 C **不是一个具体威胁模型，而是一个候选类别**。在未选定具体机制/系统之前，不能认定"哪些字段可见"，也不能把它写成唯一成立的主实验架构。
- 若未来保留架构 C，任务包要求必须逐项明确：具体机制或已有系统、服务端是否见结果 ID / 数量 / 访问模式 / 轮次时间、是否持明文 ACL、是否有填充 / 访问模式隐藏 / ID 轮换。**缺任一项则不得进入实验设计**。
- 架构 C 的实现（ORAM/PIR/TEE/MPC/ZKP）本轮禁止实现；本节只指出"不同机制可见性不同"，不做机制选型。

## 4. 服务端可观察字段契约（本轮新增，核心交付）

下表是回答"能否仅凭可见轨迹推断权限状态"的**必答契约**。每项标注：可见 / 不可见 / 需要实现核验。基础模型 $=$ THREAT_MODEL.md 的保守基线；任何"需要实现核验"项在目标系统中确认前，不得进入攻击者特征。

| # | 字段 | 判定 | 依据 / 条件 |
|---|---|---|---|
| 1 | 跨调用可关联的 opaque document ID | **需要实现核验** | 基础模型假设可见（SAGE 前提）；但 ID rotation / 每窗口 pseudonym 会削弱。须确认服务端拿到的是稳定 opaque ID 还是轮换 ID；语义化 ID（`confluence:<SPACE>`）禁止作正式特征 |
| 2 | 每次请求是否独立发送 | **需要实现核验** | 决定第 3–5 项是否成立；客户端批量提交则调用顺序不可见 |
| 3 | 每次请求返回 ID 集合 | **可见（若 #2 独立）** | 服务端构造响应即知 |
| 4 | 返回数量 / rank 顺序 | **可见（若 #2 独立）** | 服务端构造响应即知；rank 是否被服务端保留需按实现确认 |
| 5 | 请求时间戳 | **需要实现核验** | 仅服务端 API 日志实际记录时可用；ASQ 数据集本身无墙钟时间 |
| 6 | 稳定的**主体伪标识** | **需要实现核验**（关键） | 见 §4.1；若无，逐主体权限状态变化推断不可行 |
| 7 | **session / 任务标识** | **需要实现核验**（关键） | 见 §4.2；若无，须靠时间戳切分，产生误差 |
| 8 | 查询明文 | **依执行模型而定（R0.2.1 修订）** | A1 本地检索：无外包服务端，本地检索进程可见；A2 明文外包：服务端可见，退化为普通语义分类（只能作 `QUERY-VISIBLE DIAGNOSTIC`）；A3 合规后端：需逐项核验后才标不可见。当前 `NO VERIFIED QUERY-PRIVATE RETRIEVAL BACKEND` |
| 9 | 查询向量 | **需区分表示类型** | 明文向量 / 加密向量 / 受保护表示三者可见性不同；明文向量有嵌入反演风险，属另一问题 |
| 10 | ACL 与角色标签 | **不可见（基础模型）** | 服务端持 ACL 的架构 B 属循环论证，另列 |

### 4.3 执行模型对齐（R0.2.1 新增，前置于 §4 字段契约）

字段契约的"可见/不可见"判定依赖一个必须先确定的**执行模型**（详见 `AGENT_GENERATION_AUDIT.md` Query Privacy 章节）：

| 模型 | 执行方式 | 查询明文可见性 | 对本问题的地位 |
|---|---|---|---|
| A1 | Agent + Retriever 均本地（ASQ 默认） | 无外包服务端；本地检索进程可见 | 可验证 Agent 生成与 ACL 因果机制，但**不构成外包服务端实验** |
| A2 | 明文查询发往外包服务，服务端执行 BM25 | 服务端可见 | 只能作 `QUERY-VISIBLE DIAGNOSTIC`；不得写成隐私条件下泄漏 |
| A3 | 受保护查询表示 + 具体隐私保护检索 | 取决于协议，逐项核验 | 只有经核验的具体后端才可能符合核心威胁模型；当前无已核验后端 |

**后果**：§4 字段契约与架构 A 的间接泄漏因果链，只有在确定具体执行模型后才有确定的可见性判定。当前 ASQ 路线落在 A1，缺少一个"服务端只看到受保护查询 + 可见轨迹"的合规 A3 后端；这**不否定**架构 A 的因果关系假设，但使正式外包服务端实验暂不可执行。

### 4.1 三个标识必须严格区分

- **主体伪标识**：服务端可见的稳定 token（如 API key 哈希、租户 ID、会话 cookie 的稳定部分）。作用是**跨会话关联同一主体**，但**不能映射到真实姓名/角色真值**。它使"逐主体的权限状态变化检测"在服务端视角有可关联对象。
- **session / 任务标识**：区分同一主体的不同 Agent 任务。没有它就无法判断哪些检索请求属于同一轮任务。
- **真实身份**：`asking_user` 等研究者侧字段，**攻击者不应获得**。

**硬规则**：研究者侧的 `subject_id` / `qid` / `asking_user` **不是服务端可见字段**，不得直接塞进攻击者特征。它们只能用于研究者侧构造真值与数据划分。

**若无稳定主体伪标识**：逐主体的权限状态变化推断缺少关联条件 → 该项**不可评估**，不得用研究者侧字段补齐。此时仅可能做"轨迹级/批次级"的粗粒度状态检测，且须明确其粒度。

### 4.2 若无 session 标识：时间戳切分与误差

若服务端只见时间戳、无 session token，则只能按请求时间间隔做会话切分（例如间隔超过阈值 θ 即切分为新任务）。误差来源须明确写出：
- 同一主体相邻任务间隔小于 θ → **任务合并**（把一个 session 的多步轨迹混入另一个）；
- 单个任务内部思考/生成耗时超过 θ → **任务割裂**（一个 session 被拆成多个）；
- 并发任务交错 → **轨迹串线**。

这些误差会直接污染"同一任务、不同权限"的对照 A——若任务边界切错，首轮零点检验就失效。因此 session 关联是架构 A 对照实验能否成立的前置条件，不是可选项。

## 5. 三架构对照总表（修订）

| 维度 | A 客户端过滤 | B 服务端过滤 | C 加密过滤（按具体机制） |
|---|---|---|---|
| 服务端持明文 ACL | 否 | **是（已知）** | 否，但可见性随机制而定 |
| 直接泄漏（过滤结果 ID） | 否 | 是（已知） | 视填充/机制 |
| **间接泄漏（后续轨迹）** | **可能——本修订版主场景** | 后果已知 ACL，无推断价值 | 视机制（轮次/时间多不可用隐藏） |
| 首轮返回是否一致（固定任务） | 是（零点检验） | 否（按权限过滤） | 视机制 |
| 推断权限状态是否循环论证 | 否 | **是** | 否 |
| 主场景裁定 | **首选（待实验）** | 否（除非改攻击者定义） | 候选类别，须先选定具体机制 |

## 6. 对核心问题的直接回答（修订）

> 能否仅凭服务端可见轨迹推断权限状态变化？

- **架构 A**：存在明确的间接泄漏因果链（ACL→上下文→后续查询→可见轨迹）；是否被任务语义/随机性淹没**须由对照实验判定**，不能实验前排除。这是本修订版要检验的首要假设。
- **架构 B**：攻击者已知 ACL，循环论证 → 不构成有效研究问题。
- **架构 C**：须先选定具体机制并逐项确定可见字段，当前**不能**断言它唯一成立，也不能断言它不成立。

**当前状态**：真正的阻塞不是"确认架构 C"，而是**确定一个真实、可复核的服务端观测模型**（含 §4 字段契约、主体/session 关联、以及 §4.3 执行模型）。该模型可以是架构 A 或某个具体架构 C，不得预先指定。R0.2.1 新增：即使选定架构 A，仍需一个合规的查询隐私执行后端（A3）才能做"服务端看不到查询明文"的正式实验；ASQ 默认 A1 本地检索只能验证因果机制，当前 `NO VERIFIED QUERY-PRIVATE RETRIEVAL BACKEND`。

## 7. 证据与纪律声明
- 可见性来自威胁模型定义、源码机制（`AGENT_GENERATION_AUDIT.md`）与数据流位置推理，非某个具体系统的实测；不把架构假设写成已部署事实。
- 未实现 ORAM/PIR/TEE/MPC/ZKP；架构 C 各机制的可见性是基于一般条件的推断，具体系统须单独审计。
- 混合信号（任务自适应 + 权限过滤）视为实验要分离的混杂变量，不在实验前判定其无研究价值——这是本版相对初稿的关键修正。
