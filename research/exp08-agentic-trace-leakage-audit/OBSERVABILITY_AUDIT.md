# OBSERVABILITY_AUDIT.md — ACL 执行位置与外包检索服务可见性

任务：EXP-02-R0.1 Phase 4。性质：**威胁模型核验**，只界定"不同架构下服务端实际可见什么"，不实现 ORAM/PIR/TEE/MPC/ZKP。核心问题：在不让攻击者看到任务明文、角色标签或 ACL 的前提下，它能否仅凭真实可见的检索轨迹推断权限状态变化？本文件给出回答该问题所需的可观察性前提。

攻击者定义（沿用 `THREAT_MODEL.md`）：被动、持久观察的外包检索服务（honest-but-curious），跨调用持久记录。基础威胁模型假设它**看不到**查询明文、文档内容、真实 ACL、用户角色标签、Agent 内部推理、客户端本地过滤结果。下文逐架构核对该假设是否成立。

---

## 0. 一句话结论

**"服务端能否从轨迹推断权限状态"取决于 ACL 在哪里执行**：
- 架构 A（客户端过滤）：服务端只看到**过滤前的候选轨迹**，与权限状态在结构上**解耦**——对同一查询，不同权限用户触发的服务端请求往往相同；权限信号主要落在服务端看不到的客户端过滤结果里。推断论据薄弱。
- 架构 B（服务端过滤）：服务端**本就持有 ACL 与用户身份**。把"它从轨迹推断 ACL"当成果是**把已知信息包装成推断**，研究意义不成立。
- 架构 C（加密/隐私保护过滤）：这是唯一在"服务端不公开完整策略"前提下仍可能泄漏结果 ID / 数量 / 访问模式的架构，也是唯一使"不看到 ACL 但推断权限状态"这个问题**在威胁模型上自洽**的架构；但泄漏是否可归因于**权限状态**而非任务语义，仍需实验区分（见 `MINIMAL_EXPERIMENT_DESIGN.md`）。

因此，最小实验必须**明确声明所选架构**，否则"服务端可见字段"与"推断目标"会自相矛盾。

---

## 1. 架构 A：客户端 ACL 过滤

**流程**：检索服务返回候选文档（不感知 ACL）→ 客户端按本地 ACL 决定哪些候选进入 Agent 上下文 → Agent 继续多步检索。

### 1.1 服务端可见性逐项核对

| 信息项 | 服务端是否可见 | 依据 / 条件 |
|---|---|---|
| 全部候选 ID（过滤前） | **可见（是）** | 检索响应就是候选集；服务端构造并发送它 |
| 最终进入 Agent 的 ID（过滤后） | **不可见** | 过滤在客户端本地完成，未回传（基础威胁模型假设） |
| 过滤前数量 | **可见** | 等于候选集大小（服务端自己返回） |
| 过滤后数量 | **不可见** | 客户端本地结果，除非 Agent 因只拿到少量文档而发起**不同的后续查询**——这是间接信号，见 1.2 |
| 每轮请求时间与顺序 | **可见（条件）** | 仅当客户端把每次检索作为独立请求发出；若客户端缓存/批量，则顺序在服务端不可见 |
| 查询明文 | 基础模型假设不可见；但**若用向量检索，查询向量可能随请求发送**——须按实现确认 | 任务包要求逐项核实，不能默认 |

### 1.2 权限信号是否进入服务端轨迹
- 在架构 A 中，权限判断发生在**服务端视野之外**。对同一检索请求，高权限与低权限用户得到**相同的候选集**；差异只体现在客户端丢弃了哪些文档。
- 唯一的间接通道：低权限用户过滤后上下文变少 → Agent 生成**不同的后续查询** → 服务端看到不同的第二轮请求。但这个信号是"任务自适应行为"与"权限过滤"的**混合**，无法在服务端单独归因于权限状态（对照 B/C 正是为分离它而设计）。
- 若后续查询明文对服务端不可见（基础假设），服务端只剩"轮次数、返回数量、调用时间"等弱信号，权限状态推断的论据进一步削弱。

### 1.3 裁定
架构 A 下，"服务端从轨迹推断授权范围/权限状态"**缺乏直接信号通道**：权限决策不在服务端可见面内。若实验在架构 A 下声称推断成功，必须先排除"信号其实来自任务语义或查询明文"。**该架构不宜作为证明权限状态泄漏的主实验架构**，可作为"无直接信号"的阴性对照。

## 2. 架构 B：服务端 ACL 过滤

**流程**：检索服务持有 ACL 与用户身份，按用户权限执行过滤后返回授权文档。

### 2.1 服务端可见性逐项核对

| 信息项 | 服务端是否可见 | 依据 / 条件 |
|---|---|---|
| 是否持有 ACL | **是（定义性）** | 过滤执行依赖 ACL；服务端必须持有或可查询它 |
| 能否关联用户身份 | **是（定义性）** | 按用户过滤需知道请求主体 |
| 授权谓词 / 过滤规则 | **可见** | 服务端执行过滤，规则在执行路径上 |
| 过滤结果（最终 ID） | **可见（它自己产出）** | 返回给客户端的即授权后集合 |
| 过滤前后数量 | **可见** | 服务端知道候选数与返回数 |
| 每轮请求时间/顺序 | **可见（条件同 A）** | 取决于是否独立请求 |

### 2.2 研究意义重评估（任务包明确要求）
- 若攻击者=检索服务本身，则 **ACL 与身份是它执行过滤的已知输入**。称它"从轨迹推断出权限状态"是**把已知信息当作推断成果**：它无需从轨迹反推，因为权限集合本就在它的访问控制决策里。
- 因此架构 B 下，"服务端推断 ACL"作为隐私攻击**不成立**（循环论证）。
- 唯一仍可能成立的子问题：攻击者是服务内部一个**只接触请求日志、不接触 ACL 数据库**的组件（如日志分析/缓存/计费子系统）。此时 ACL 对它不直接可见，轨迹可能泄漏权限。但这**改变了攻击者定义**，必须在威胁模型中显式声明，且不能代表"外包检索服务"这一基础对手。按任务包执行纪律（"若某种系统架构暴露额外信息，须单独说明，不能默认加入基础威胁模型"），此变体单列，不并入基础结论。

### 2.3 裁定
架构 B（攻击者=检索服务）下，推断 ACL 的研究意义**不成立**——已知信息不是推断成果。若改用"日志侧观察者"攻击者，须重写威胁模型并作为独立场景，不得混用基础对手定义。**架构 B 不宜作为本候选问题的主实验架构。**

## 3. 架构 C：加密 / 隐私保护 ACL 过滤

**流程**：在不向服务端公开完整授权策略的前提下执行过滤（例如加密策略匹配、PIR/ORAM 式检索、TEE 内过滤等）。本节**只界定威胁模型，不实现任何机制**。

### 3.1 服务端可见性逐项核对（取决于具体机制，逐项标注）

| 信息项 | 是否仍可能泄漏 | 说明 |
|---|---|---|
| 结果 ID（返回文档） | **可能泄漏** | 除非机制对结果集做隐藏（如 ORAM 读取路径混淆 / 填充），否则服务端可见返回了哪些加密文档句柄 |
| 访问模式（哪些索引节点/桶被触碰） | **可能泄漏** | 加密过滤若仍触碰与权限相关的索引分区，访问模式可泄漏"该用户能访问哪个分区" |
| 结果数量 | **可能泄漏** | 除非填充到固定上界，返回条数本身是强信号（低权限→少文档） |
| 请求元数据（时间/轮次/调用次数） | **可能泄漏** | Agent 多步行为的时间与轮次通常不在加密保护范围 |
| 完整授权策略 | **不公开（定义性）** | 这是架构 C 与 B 的根本区别：服务端不持有明文 ACL |
| 查询内容 | 视机制而定 | 基础模型假设不可见；若查询向量/明文随请求发送则可见（须按实现确认） |

### 3.2 为何这是唯一自洽的主实验架构
- 架构 C 同时满足两个条件：(i) 服务端**不直接持有明文 ACL**（所以"从轨迹推断权限状态"不是循环论证）；(ii) 仍有**部分可观察轨迹**（结果 ID / 数量 / 访问模式 / 轮次），使推断有输入。
- 这与 SAGE / PP-RFANNS 的威胁模型一致：它们正是在"服务端看到访问模式与结果 ID，但不知语义标签/内容"的设定下做推断。因此架构 C 是"我们的问题相对 SAGE 是否有新增量"的**正确对照场景**。
- 注意：架构 C 的机制实现（ORAM/PIR/TEE/MPC/ZKP）本轮禁止实现；本文件只说明"若采用此类机制，哪些信息仍在基础模型下可见"，供威胁模型自洽性判断。

### 3.3 关键风险：权限信号 vs 任务语义的混淆
- 即便在架构 C 下，服务端看到的"多步检索、结果数量变化"也可能由**任务内容差异**驱动，而非权限状态。例如用户问了更难的问题→更多轮检索，与权限无关。
- 若服务端能看见查询明文，它可直接按语义分类任务/角色，无需权限信号（命中 NO-GO 条件：依赖不可见/额外字段）。
- 因此实验必须用**对照 A/B/C**（同一任务不同权限、不同角色相同任务、相同权限不同任务）把权限信号从任务语义中分离，并用 opaque ID 排除命名空间伪相关（对照 D）。

## 4. 三架构对照总表

| 维度 | A 客户端过滤 | B 服务端过滤 | C 加密/隐私保护过滤 |
|---|---|---|---|
| 服务端持有明文 ACL | 否 | **是（已知）** | 否 |
| 服务端见过滤前候选 ID | 是 | 是 | 视机制 |
| 服务端见过滤后/返回 ID | 否 | 是 | **可能（视机制）** |
| 服务端见结果数量 | 过滤前可见 | 可见 | **可能泄漏（若未填充）** |
| 服务端见访问模式 | 视检索索引 | 视检索索引 | **可能泄漏** |
| 服务端见轮次/时间 | 条件可见 | 条件可见 | 条件可见 |
| "推断权限状态"是否循环论证 | 否（但无信号） | **是（ACL 已知）** | 否（自洽） |
| 是否适合作为主实验架构 | 否（阴性对照） | 否（除非改攻击者定义） | **是（唯一自洽）** |

## 5. 对核心问题的直接回答

> 能否在不让攻击者看到任务明文、角色标签或 ACL 的前提下，让它仅凭真实可见的检索轨迹，推断出权限状态变化？

- **架构 A**：结构上缺少直接信号通道；除非通过"过滤导致后续查询变化"这一混淆通道，否则不可行 → 不支持。
- **架构 B**：攻击者已知 ACL，问题退化为循环论证 → 不构成有效研究问题。
- **架构 C**：威胁模型自洽、有可观察输入，是本问题的**唯一成立场景**；但成立不等于已证明——是否真的存在可归因于权限状态（而非任务语义/命名空间）的信号，必须由 `MINIMAL_EXPERIMENT_DESIGN.md` 的对照实验回答。本轮不实施实验，故**结论为"存在自洽场景，但信号是否存在尚未验证"**。

## 6. 证据与纪律声明
- 三架构的可见性来自威胁模型定义与数据流位置推理，非来自某个具体系统的实测；不把架构假设写成已部署事实。
- 未实现 ORAM/PIR/TEE/MPC/ZKP；架构 C 的"可能泄漏"是基于"未填充/未混淆"的一般条件推断，具体机制须单独审计。
- 查询明文是否可见按实现逐项确认，未默认加入基础威胁模型（`THREAT_MODEL.md` 一致）。
